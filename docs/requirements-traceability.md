# Requirements Traceability Matrix

This matrix maps examination requirements to implementation ownership, executable interfaces, evidence, demonstrations, and current status. Status is based on repository contents and validation performed against the current PoC environment; source code or a test definition alone is not treated as successful execution evidence.

## Status definitions

- **Implemented** — executable source or configuration exists.
- **Unit Validated** — isolated backend or frontend behavior tests executed successfully.
- **Integration Validated** — the specifically stated multi-component flow executed successfully.
- **Platform Validated** — deployment, manifest, dependency or configuration checks executed successfully, but the full user journey has not necessarily run.
- **End-to-End Validated** — an authenticated user-facing flow executed through its real application boundaries.
- **Pending / Not Verified** — implementation may exist, but no successful evidence exists for the stated boundary.

No Customer Identity and Account Management requirement is labelled complete. The retained integration report at `test-results/integration/customer-identity.xml` contains seven skipped tests, so it is collection evidence rather than end-to-end success evidence. Successful checks and unresolved evidence are recorded in the [Customer Identity validation record](evidence/customer-identity-validation.md).

For Product Catalogue and Inventory, **Unit Validated** means the current 60-test
catalogue-service suite executed successfully. **Platform Validated** means the relevant
manifests and current internal workloads were checked; it does not prove the user
workflow. The focused React suite executed six tests. The explicitly enabled catalogue
integration suite subsequently passed all 11 authenticated Gateway/platform scenarios
in 79.09 seconds with zero failures, errors or skips. Separate manual browser evidence
is recorded where a user-facing flow was exercised.

## Current evidence boundary

The repository contains independently buildable services; implemented customer,
catalogue/inventory and order APIs; React identity, customer, catalogue, inventory and
order screens; fixed API Gateway routes; an import-oriented Terraform baseline; and
Kubernetes resources for PostgreSQL, Keycloak, Redis, Kafka, customer-service,
catalogue-service, order-service and API Gateway. Current live checks confirm the single
kind node and these internal workloads are Ready. Catalogue validation records 60 backend
tests and migration head `004_inventory_reservations`; Order records 46 backend tests and
migration head `004_order_outbox_conventions`. The Order E2E evidence records a deployed
Gateway flow and broker recovery, not merely source-level intent.

This evidence proves the stated catalogue/inventory browser flow and the API-driven Order
Keycloak → API Gateway → order-service → catalogue-service flow. It does not prove a
Kubernetes-deployed frontend, a retained browser-driven order execution, the
inventory-statistics browser journey, category parent editing, or a complete
customer-service identity journey. Customer integration retains seven skips. It also does
not prove SMTP password recovery, verified email, MFA, durable identity-event export,
production rate limiting, Terraform-applied infrastructure, a retained Jenkins controller
run, production readiness, or any form of host-level high availability.
