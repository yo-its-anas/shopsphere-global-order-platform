# ShopSphere Wazuh Security Monitoring (PoC & Production Evolution)

This document records the architectural decisions, resource constraints, and operational scope for the Wazuh security monitoring deployment in the ShopSphere Enterprise Platform.

## 1. Minimal Defensible Architecture (PoC)

To provide meaningful security monitoring without introducing unacceptable resource risks (such as Out-Of-Memory kills) to the existing Google Cloud VM (n2-standard-8, 32GB RAM), we have deliberately **excluded** the Wazuh Indexer (Elasticsearch/OpenSearch clone) and Wazuh Dashboard. 

Running a full JVM-based SIEM indexing stack on a single node already hosting PostgreSQL, Redis, Kafka, Loki, Prometheus, Grafana, Keycloak, and 5 FastAPI microservices creates severe starvation risks.

Instead, the PoC utilizes a **decoupled, resource-conscious topology**:

```text
+-------------------------------------------------------------+
|                     Kubernetes Cluster                      |
|                                                             |
|   [ shopsphere-security ]                                   |
|                                                             |
|      +-----------------+         +-------------------+      |
|      |  Wazuh Agent    |         |   Wazuh Manager   |      |
|      |  (DaemonSet)    | ------> |   (Deployment)    |      |
|      +-----------------+  1514   +-------------------+      |
|              |            TCP             |                 |
|              v                            v                 |
|    +-------------------+        +--------------------+      |
|    | Host OS Mounts    |        | /var/ossec/logs/   |      |
|    | (/var/log, /etc)  |        | alerts/alerts.json |      |
|    +-------------------+        +--------------------+      |
+-------------------------------------------------------------+
```

### 1.1 Resource Allocation
*   **Wazuh Manager:** 
    *   Requests: CPU 100m, Memory 512Mi
    *   Limits: CPU 500m, Memory 1Gi
*   **Wazuh Agent:**
    *   Requests: CPU 50m, Memory 128Mi
    *   Limits: CPU 200m, Memory 256Mi

### 1.2 Monitoring Scope
*   **What is monitored:**
    *   **GCP VM Host Activity:** Authentication events (SSH, sudo via `/var/log/auth.log`), system logs (`/var/log/syslog`).
    *   **File Integrity Monitoring (FIM):** Scoped exclusively to critical host configuration paths (`/etc/passwd`, `/etc/shadow`, `/etc/hosts`).
    *   **Kubernetes Node Security:** Basic container runtime and kubelet logs (if exposed to syslog/journald).
*   **What is NOT monitored:**
    *   **Application Secrets:** The agent does not read mounted Kubernetes Secrets or `.env` files.
    *   **Volatile Directories:** Massive volatile data paths (e.g., PostgreSQL PVCs, Kafka logs, `/var/lib/docker/containers`) are explicitly excluded to prevent CPU spikes and I/O exhaustion.
    *   **No Public Interfaces:** No Wazuh API or Dashboard is exposed publicly.

### 1.3 Security Event Demonstration
To demonstrate the capability, the Wazuh Agent monitors host authentication events and file integrity. Operational engineers can verify alerts by inspecting the structured JSON alert log generated by the Wazuh Manager directly, or by routing it to the existing Loki/Grafana observability stack.

## 2. Production SIEM Evolution

While the minimal architecture proves the capability, an enterprise production deployment must evolve to a highly available, centralized SIEM structure.

### 2.1 Full SIEM Topology
In a multi-node production GKE environment, the architecture will transition to:

1.  **Dedicated SIEM Cluster / SaaS:** Wazuh Indexer and Dashboard must run on dedicated nodes optimized for high disk I/O and memory (e.g., memory-optimized instances), or utilize a managed SaaS SIEM.
2.  **Highly Available Managers:** Deploy a Wazuh Manager cluster behind an internal LoadBalancer to handle high-volume agent connections.
3.  **Forwarding & Alert Routing:** The Wazuh Manager will forward indexed alerts securely to an enterprise SOC, triggering automated incident response runbooks (e.g., PagerDuty, Slack) based on severity thresholds.
4.  **Workload Identity:** Wazuh Agents will enroll using secure workload identity and auto-enrollment passwords retrieved dynamically from a Secret Manager, rather than static environment variables.
