# ShopSphere Grafana Dashboards and Operations

This document outlines the purpose, audience, and query structure of the Grafana dashboards provisioned for the ShopSphere Enterprise Platform.

## 1. ShopSphere Service Overview
**Audience:** SREs, Platform Engineers, and On-Call Responders
**Purpose:** Provide a high-level view of core service health (`api-gateway`, `customer-service`, `catalogue-service`, `order-service`) at a glance.

**Main Panels & Query Purpose:**
*   **Service Up/Down (Stat):** Uses Prometheus `up{job="shopsphere-applications"}` to instantly flag if a service target cannot be scraped.
*   **Request Rate (Time Series):** Calculates `sum by (service) (rate(http_requests_total[1m]))` to show current throughput per service.
*   **Error Rate (Time Series):** Calculates `sum by (service) (rate(http_requests_total{status=~"5.."}[1m]))` to identify active server-side HTTP failures.
*   **P95 Latency (Time Series):** Computes `histogram_quantile(0.95, sum by (le, service) (rate(http_request_duration_seconds_bucket[5m])))` to show the 95th percentile response time for each service.
*   **Pod Restarts (Time Series):** Uses `sum by (pod) (kube_pod_container_status_restarts_total)` to quickly highlight crash loops.

## 2. API Performance
**Audience:** Software Engineers and Application Developers
**Purpose:** Drill down into API routes, methods, and status codes to optimize performance.

**Main Panels & Query Purpose:**
*   **Requests by Status Code (Time Series):** Sums the request rate grouped by HTTP status code. Helps spot sudden spikes in 4xx or 5xx codes.
*   **Slowest Routes (P99) (Time Series):** Uses `histogram_quantile(0.99, ... rate(http_request_duration_seconds_bucket))` grouped by `route` and `method`. This strictly avoids using high-cardinality IDs (like customer ID) by relying on the bounded templated route label generated by FastAPI's middleware.

## 3. Order Processing Operations
**Audience:** Business Operations and Product Managers
**Purpose:** Monitor technical/business-safe operational metrics related to order lifecycle and inventory, without duplicating executive revenue reporting.

**Main Panels & Query Purpose:**
*   **Checkout Attempts vs Success (Time Series):** Measures the rate of `shopsphere_checkout_attempts_total` grouped by status (success/failure) to monitor checkout flow conversion/reliability.
*   **Inventory Reservation Operations (Time Series):** Monitors the rate of `shopsphere_inventory_reservations_total` to track successful and failed stock reservations during order placement.
*   **Outbox Event Publication (Time Series):** Monitors the rate of `shopsphere_outbox_events_published_total` to ensure transactional domain events are successfully relayed to Kafka.

## 4. Platform Health
**Audience:** Platform Engineers and SREs
**Purpose:** Monitor the underlying Kubernetes node, CPU, and memory utilization for the single-node PoC cluster.

**Main Panels & Query Purpose:**
*   **Nodes Ready (Stat):** Checks `kube_node_status_condition{condition="Ready"}` to verify the underlying VM/Node health.
*   **CPU Usage by Namespace (Time Series):** Tracks `rate(container_cpu_usage_seconds_total[5m])` across namespaces to identify noisy neighbors.
*   **Memory Usage by Namespace (Time Series):** Tracks `container_memory_working_set_bytes` to monitor memory pressure and potential OOM kills.

## Trace Correlation
Loki data sources are configured to automatically extract `trace_id` from structured JSON logs via the `trace-correlation` derived field. When viewing logs in the Loki Explorer, a recognized trace ID will become a clickable link, although trace visualization requires an OpenTelemetry backend (like Tempo or Jaeger) which is out of scope for the current PoC, Grafana provides the framework for this seamless context pivot once trace storage is deployed.

## Known PoC Limitations
*   **Monolithic Data Stores:** Prometheus and Loki are deployed as single replicas with local persistent volumes. They do not provide high availability (HA).
*   **Data Retention:** Data is retained for conservative periods (e.g., 48 hours for Loki, default 15d for Prometheus) to fit within strict disk quotas.
*   **Internal Access Only:** Grafana is deliberately exposed as a `ClusterIP` service without ingress. Access requires authenticated `kubectl port-forward` directly into the `shopsphere-monitoring` namespace.
*   **Trace Storage:** While the application outputs W3C trace context, there is currently no trace database (e.g., Tempo) provisioned to visualize the entire distributed trace.
*   **Pod Limits:** Due to the single VM running Kind, all components are heavily CPU/Memory constrained, meaning extreme traffic spikes may result in degraded dashboard responsiveness or Promtail backpressure.
